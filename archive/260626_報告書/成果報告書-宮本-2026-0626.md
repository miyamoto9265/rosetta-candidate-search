# 背景

脳参照アーキテクチャ（BRA）駆動開発では、BRAデータと呼ばれる脳型アーキテクチャの設計仕様書の作成を行う。BRAデータはこれまで神経科学や工学の知見を基に人手で作成されてきたが、大規模言語モデル（LLM）技術を取り入れることで、BIFデータの自動構築やBRAデータの自動設計・自動評価システムの開発が行われてきた。一方で、そのように自動構築されたデータベースに含まれる解剖学的領域名を、BRAデータとして定める標準化された命名体系に変換するツールの開発が急ぎ必要となった。本業務では、HOMBA（Harmonized Ontology of Mammalian Brain Anatomy）オントロジーを基盤として、論文等のテキストから抽出された脳領域名を標準タームへ自動変換するツール「ROSETTA Candidate Search（RCS）」を開発した。HOMBAは Allen Institute が開発した2,341の脳・脊髄構造を含む階層的な種横断オントロジーであり、ヒト・霊長類・げっ歯類の構造間で用語が統一されている。

本業務で行った作業の一覧は以下の通りである。

1. HOMBAオントロジーDBの整備（タイポ修正・略語辞書構築・補助リソース選定）

# [作業1] RCSの開発

## 1) HOMBAオントロジーDBの整備（タイポ修正・略語辞書構築・補助リソース選定）

検索エンジンの精度は、変換先となるオントロジーの品質に大きく依存する。本作業では、現在RCSが使用しているHOMBAオントロジーCSVに含まれるタイポ（綴り誤り）の修正を行い、検索辞書の基盤品質を確保した。

### タイポ修正

HOMBAオントロジーの全2,341エントリを精査し、以下のカテゴリのタイポを特定・修正した。修正済みのオントロジーは納品物一覧の HOMBA_v1_fixed.csv を参照のこと。

| カテゴリ | 修正件数 | 代表例 |
|---------|---------|--------|
| 単純な綴り誤り | 18件 | promotor → premotor, auditiory → auditory, magocellular → magnocellular |
| スペース欠落 | 3件 | rostraldivision → rostral division, oflower → of lower |
| 余分な文字 | 2件 | densocelllular → densocellular, subdivsion → subdivision |
| ラテン語綴り誤り | 3件 | terminaris → terminalis, infundubular → infundibular, nulceus → nucleus |
| 余分なスペース | 5箇所 | ダブルスペースの修正 |

これらのタイポ修正により、正規化処理やテキストマッチングにおけるノイズを排除し、後段のアルゴリズム精度向上の基盤を確立した。

### 略語辞書・エイリアス辞書の構築

HOMBAの調査において特定された表記揺れの課題（人名由来名、略称不統一、方向用語の不統一等）に対応するため、以下の辞書リソースを構築した。辞書構築は2)（アルゴリズム実装）と4)（評価・改善）と密接に連動し、イテレーティブに拡充した。辞書の詳細は「RCSアルゴリズム仕様資料」を参照のこと。

| 辞書 | エントリ数 | 用途 |
|------|-----------|------|
| エイリアス辞書（homba_alias_rules.csv） | 125件 | 同義語・語順変換・エポニム対応・スペル変換 |
| 略語辞書（homba_abbrev_rules.csv） | 38件 | クエリ側の略語展開（LC→locus coeruleus等） |
| トークン制御辞書（homba_token_rules.csv） | 57件 | ストップワード・方向修飾語・弱トークンの分類 |

## 2) 多戦略並列検索アルゴリズムの実装（前処理・エイリアス照合・Fuzzy・BM25・階層構造反映）

### 実装方針の策定

RCSのアルゴリズム設計に先立ち、LLM（大規模言語モデル）との対話を通じて実装方針を策定した。策定した方針は3段階パイプラインアーキテクチャ（前処理→候補生成→リランキング）であり、候補生成段階では完全一致・あいまいマッチ・BM25の3戦略並列方式、リランキング段階ではSapBERTなどの生物医学埋め込みモデルによるセマンティックリランキングを計画した。

しかし、実装と評価を進める中で、以下の判断に至った。

**埋め込み空間によるセマンティックリランキングの見送り**: 脳領域名は単語レベルの短いフレーズであり、埋め込み空間における意味距離が十分に機能しない可能性が高いと判断した。例えば「lateral nucleus」と「medial nucleus」は埋め込み空間上では近接するが、解剖学的には全く異なる構造を指す。このため、埋め込みモデルによるリランキングは当面行わず、文字列レベルの検索アルゴリズムの改善と辞書拡充によって精度向上を図る方針とした。

### 最終的なアルゴリズム構成

最終的に実装したRCSのアルゴリズムは、依存ライブラリを持たない純Python実装であり、検索エンジン本体は rosetta_candidate_generator.py として納品物一覧に含まれる。アルゴリズムの構成は以下の通りである。詳細は「RCSアルゴリズム仕様資料」を参照のこと。

**Stage 1: 前処理（正規化・クエリ変換生成）**

入力クエリに対して以下の変換を適用し、複数のクエリバリアントを生成する。

| 処理 | 内容 |
|------|------|
| Unicode正規化 | NFKC正規化、記号・アポストロフィ除去 |
| ケース正規化 | 小文字統一 |
| 記号・空白正規化 | ハイフン・アンダースコアをスペースに統一 |
| 左右情報の除去 | left/right/bilateral等の方向語を除去 |
| 括弧内情報の分離 | 括弧内テキストの分離と独立クエリ化 |
| エイリアス辞書適用 | 同義語展開（双方向） |
| 略語辞書適用 | クエリ側のみの略語展開 |

**Stage 2: 候補生成（3戦略並列）**

3つの独立した検索戦略で候補を生成し、和集合を取る。

**2a. 完全一致検索**: 正規化済みクエリでエイリアスマップを直接ルックアップする。HOMBAの公式名・略称・DHBA名・階層情報から展開した全エイリアスをキーとするハッシュマップを事前構築する。

**2b. あいまい文字列マッチング（Fuzzy）**: SequenceMatcher比率、バイグラム・トライグラムDice係数、トークンJaccard類似度、文字列包含度を組み合わせた複合類似度スコアで候補を生成する。

**2c. BM25トークン検索**: HOMBAの全エイリアスを「文書」として転置インデックスを構築し、BM25Okapiスコアリングで候補を生成する。複合名（multi-word term）の部分一致や語順の違いに対応する。

**Stage 3: スコアリングとランキング**

以下の要素を統合して最終スコアを算出する。

| 要素 | 役割 |
|------|------|
| メソッドスコア統合 | exact/fuzzy/bm25の各スコアを重み付き統合 |
| 修飾語マッチング | クエリの修飾語（anterior, dorsal等）と候補エイリアス間の一致度 |
| 特異性ペナルティ | クエリより詳細な候補に対する過適合防止 |
| 共通親ノードプロモーション | 複数の兄弟候補が出現した場合に親ノードを昇格 |

**エイリアス展開**

HOMBAの各エントリに対して以下の展開を事前に行い、検索インデックスの網羅性を高める。

- 括弧内テキストの分離と独立エイリアス化
- カンマ区切りの語順反転（"X, Y" → "Y X"）
- エイリアス辞書の双方向適用

## 3) テストデータの作成（ゴールドスタンダード系・引っかけ問題系・動物種別オントロジー網羅系・実論文収集系）

### テストデータの設計方針

RCSの評価・改善に用いるテストデータを4種類設計・構築した。各データセットは異なる評価観点をカバーする。

| データセット | ファイル | 件数 | 評価観点 |
|-------------|---------|------|---------|
| Core（正例） | rcs_core.csv | 231件 | 基本的な変換精度（既知の正解付き） |
| Challenge（引っかけ問題） | rcs_challenge.csv | 15件 | 曖昧性解消・HOMBAギャップ検出 |
| Species（動物種別） | rcs_species.csv | 556件 | 種横断的なオントロジー網羅性 |
| Corpus（実論文収集） | rcs_corpus.csv | 416件 | 実際の論文で使用される名称への対応 |

### Core データセット

Coreデータセットは、RCSの基本的な変換精度を評価するための正例データセットである。各エントリは入力クエリ（structure_name）、期待されるHOMBA ID、期待されるHOMBA名から構成される。

本データセットは、後述する4)のLLMを用いた自律的改善プロセスの中で、アルゴリズム改善と同時に構築された。LLMが生成したテストケースのうち、改善サイクルを経てRCSが正しく変換できるようになったものをCoreに収録し、原理的に解決困難なもの（曖昧性・オントロジーギャップ等）をChallengeに分離した。したがって、Coreデータセットに対してRCSが100%正解することは、このプロセスの帰結として必然である。

### Challenge データセット

Coreデータセットの構築過程で、正解を一意に定められない、またはオントロジー自体にギャップがあるために解決困難と判断されたケースを分離・収集したデータセットである。以下のような問題パターンが含まれる。

- 同名の構造が異なる脳領域に存在し、文脈なしでは曖昧（例：arcuate nucleus — 視床下部と延髄に同名）
- HOMBAに該当エントリが存在しない（例：inferior fronto-occipital fasciculus）
- 粒度の問題で単一エントリに対応づけられない（例：brainstem全体）

### Species データセット

ヒト・霊長類（マカクザル）・げっ歯類（ラット）の3種について、公開されているアトラスのラベルファイルから構造名を収集したデータセットである。以下のソースから構築した。

| 種 | ソース | エントリ数 |
|----|--------|-----------|
| Macaque | SARM (Subcortical Atlas of the Rhesus Macaque), mHOA2 | 約320件 |
| Rat | Waxholm Space Atlas v4 | 約230件 |

このデータセットには正解ラベルは付与されていない（正解の付与にはドメイン専門家による大規模なキュレーションが必要なため）。RCSが返す候補の妥当性はLLM評価によって行う。

### Corpus データセット

実際の神経科学論文から脳領域名を収集したデータセットである。ヒト・マカクザル・ラットの3種について、年代（1909年〜2024年）・脳領域グループ（大脳皮質・基底核・海馬・小脳・脳幹等）を網羅的にカバーする論文群から構造名を抽出した。全12論文から559件の構造名を収集し、RCSの実用的な対応力を評価するために使用する。

## 4) 定量評価（Precision／Recall／F1）と誤変換分析によるアルゴリズム改善（2〜4をイテレーティブに実施）

### 評価手法の設計

本業務の当初計画ではPrecision／Recall／F1による定量評価が想定されていたが、以下の理由から、LLMによる整合性評価を中心とした評価を行った。

**正例テストデータセットの網羅的作成が困難である理由**: RCSへの入力となるクエリ（脳領域名の表記）は、略語・同義語・エポニム・種特異的表現・タイポ等の組み合わせにより事実上無限のバリエーションが存在する。これら無限の入力パターンに対して2,341通りのオントロジーエントリから正解を一意に割り当てる作業は、網羅的に行うことが原理的に不可能である。さらに、辞書を追加するたびに新たなクエリパターンが正しくマッチするようになるため、正解の定義自体が動的に変化し、一度作成した正解データが陳腐化する。

### LLM評価の方法

LLM（DeepSeek）による3パス投票評価を実施した。各レコードについて、DeepSeek flash 2回、DeepSeek pro 1回の計3回の独立判定を行い、投票結果を集約する。

#### 評価ラベル

| ラベル | 意味 |
|--------|------|
| aligned | クエリとtop-1候補が完全に整合 |
| broader_parent | top-1は正しいが、より上位の概念を返している |
| partial_or_narrower | top-1は部分的に正しいが、より狭い/広い概念 |
| wrong | top-1が明らかに誤り |
| no_consensus | LLM間で意見が一致しない |
| ambiguous | クエリ自体が曖昧で判定不能 |
| source_or_ontology_issue | ソースデータまたはオントロジー自体の問題 |

#### 評価結果サマリ

全921件のレコードに対するLLM評価結果は以下の通りである。

| ラベル | 件数 | 割合 |
|--------|------|------|
| aligned | 475 | 51.6% |
| broader_parent | 249 | 27.0% |
| partial_or_narrower | 63 | 6.8% |
| wrong | 118 | 12.8% |
| no_consensus | 12 | 1.3% |
| ambiguous | 3 | 0.3% |
| source_or_ontology_issue | 1 | 0.1% |

投票の確信度は、high（780件, 84.7%）、medium（129件, 14.0%）、low（12件, 1.3%）であった。投票一致パターンは3-0（全会一致）が800件（86.9%）、2-1（多数決）が109件（11.8%）、1-1-1（分裂）が12件（1.3%）であった。

### 評価の特徴と正当化

本評価手法には以下の特徴がある。

**偽陽性を許容する設計**: 3パスLLM評価では、「aligned」と判定されたものが実際に正しいかどうかよりも、少なくとも「aligned」と一致判定されたものは正確である可能性が高いという前提を採用している。すなわち、不整合と判定されたもの（wrong等）の中に偽陽性（実際には正しいが不整合と判定されたケース）が含まれることを許容する。

**インクリメンタルな改善による正当化**: この評価アプローチは、整合したもの（aligned）をどんどん増やしていくインクリメンタルな改善戦略によって正当化される。各改善ラウンドにおいて、aligned件数が単調に増加し、wrong件数が単調に減少していることを確認することで、アルゴリズムの改善を確認する。正解データの網羅的な作成なしに、改善の方向性を定量的に追跡できる。

### アルゴリズム改善の実施

評価結果に基づき、以下のイテレーティブな改善を実施した。

| 改善項目 | 対応内容 |
|---------|---------|
| エイリアス辞書の拡充 | 評価でwrongとなったケースを分析し、不足していた同義語規則を追加（全125件） |
| 略語辞書の構築 | 頻出略語38件を辞書化 |
| トークン制御の最適化 | ストップワード・修飾語の分類を調整（57件） |
| スコアリングロジックの改善 | 修飾語マッチ・特異性ペナルティ・共通親プロモーションの追加 |
| エイリアス展開ロジックの改善 | 括弧内テキスト・カンマ区切りの展開規則を追加 |

改善の効果として、辞書変更に伴うtop-1の変化を追跡したところ、以下の結果を得た。

| 指標 | ベースライン | 改善後 |
|------|------------|--------|
| LLM accept (top-1正解と判定) | 689件 | 689件 |
| うち高確信 | 402件 | 402件 |
| top-1変更のうち改善 | — | 29件 |
| top-1変更のうち悪化 | — | 4件 |

### LLMを用いた自律的改善プロセス

テストデータの構築（3)）とアルゴリズム改善（4)）は、LLMを用いた自律的改善プロセスによって密接に連動して実施された。具体的には、AIコーディングツール「Cursor」のエージェント機能を活用し、以下のサイクルを繰り返した。

1. テストデータでRCSを実行
2. LLMが結果を分析し、不整合の原因を分類
3. LLMが辞書エントリやスコアリングロジックの修正提案を生成
4. 修正を適用して再評価

このプロセスにより、人手による介入を最小限に抑えながら、辞書とアルゴリズムの同時最適化を効率的に実施できた。

#### Coreデータセット構築時の自律的改善

開発初期段階では、LLMが自律的にテストケースを生成し、それに対するRCSの出力を評価・修正するサイクルを実行した。具体的には以下のラウンドを経て、テストデータとアルゴリズムを同時に改善した。

1. **Level 1**: 主要な脳領域の基本的なエントリ（基底核、大脳皮質、小脳等の代表的な構造）
2. **Round 1**: Level 1を網羅的に拡張し、略語・同義語・エポニム等の多様なクエリパターンを追加
3. **Round 3**: エッジケース（曖昧な名称、古い命名法、種特異的な修飾子等）を重点的に追加
4. **Round 4**: 大規模な追加エントリでカバレッジを向上

この段階ではLLMが生成したテストケース自体に不整合が含まれる場合があり、それをLLM自身が検証・修正することでプロセスが成立した。解決可能なものはアルゴリズム改善により正しく変換できるようにした上でCoreデータセットに収録し、原理的に解決困難なものはChallengeデータセットに分離した。

#### Species・Corpusデータセットによる自律的改善

Coreデータセットの構築が完了した後は、実データ（公開アトラスラベルや実論文から収集した脳領域名）を入力として同様の自律的改善サイクルを実行した。プロセスの構造はCore構築時と同一であるが、入力がLLM生成ではなく実データである点が異なる。実データを用いることで、実運用で遭遇する表記パターンへの対応力を直接的に改善できる。

本業務期間中に、SpeciesデータセットとCorpusデータセットを用いた改善を3ラウンド実施した。各ラウンドではRCSを全件実行し、出力の信頼度フラグ（high_confidence / needs_review / low_confidence）の分布変化によって改善を追跡した。

| データセット | 指標 | ベースライン | Round 3 |
|-------------|------|------------|---------|
| Species（542件） | high_confidence | 37.8% | 45.8% |
| Species（542件） | low_confidence | 13.7% | 9.8% |
| Corpus（379件） | high_confidence | 40.9% | 46.2% |
| Corpus（379件） | low_confidence | 25.9% | 24.0% |

各ラウンドではLLMが不整合ケースを分析し、エイリアス辞書に追加すべき規則を5ラウンドにわたり自律的に提案・適用した（エイリアスループ）。この結果、Speciesにおいてhigh_confidence率は37.8%から45.8%へ8.0ポイント改善し、low_confidence率は13.7%から9.8%へ低減した。

さらに、全921件に対してLLMによる3パス絶対評価を実施し、辞書改善前後のtop-1変化を詳細に追跡した（前述の評価結果サマリ）。評価手法および結果の詳細は「RCSテストデータ評価資料」を参照のこと。

## 5) 周辺ツールとの連携を行う

### AWS上でのAPIホスティング

RCSを外部システムから利用可能にするため、AWS Lambda + API Gatewayによる REST APIとしてデプロイした。構成は以下の通りである。

| コンポーネント | AWS サービス | 役割 |
|-------------|------------|------|
| API エンドポイント | API Gateway | HTTPS受付・CORS処理 |
| 検索エンジン | Lambda | RCS本体の実行 |
| データストア | S3 | HOMBA CSV・辞書ファイルの格納 |
| CDN | CloudFront | ドキュメントサイトの配信 |
| DNS | Route 53 | カスタムドメイン管理 |

Lambda関数は、事前構築したキャッシュ（pickle形式のインデックス）をS3から読み込むことで、コールドスタート時間を最小化している。

### API エンドポイントの引き継ぎ

API エンドポイントおよびドキュメント（使用方法・リクエスト/レスポンス仕様）を担当者（芦原氏）に引き継いだ。APIの詳細仕様は「RCS API仕様補足資料」を参照のこと。
